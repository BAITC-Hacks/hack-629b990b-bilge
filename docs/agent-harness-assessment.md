## Вывод

В проекте есть управляемый AI-workflow с двумя операциями: генерация уточняющих вопросов и предварительный список проверок Git-свидетельства. Его harness уже обеспечивает структурированный ответ, предметные ограничения, тайм-аут, fallback, сохранение результата и ручное подтверждение человеком. Модель не выбирает инструменты и не управляет многошаговым выполнением самостоятельно.

Предоставленный кейс не требует автономного агента, Agents SDK, multi-agent orchestration или отдельного harness. Он требует минимум одну содержательную AI-функцию. Наличие такой функции реализовано; полезность на разных задачах и отсутствие неподтверждённых предпосылок ещё нужно подкрепить смысловыми evals. Следующий полезный шаг — извлекать уже сообщённые факты в проверяемые предложения к карточке, чтобы пользователь не вводил их повторно.

## Три воспроизведённых ограничения

Проверки выполнены изолированно: SQLite `:memory:`, синтетические данные и подставленный HTTP-ответ модели. База демонстрации не изменялась.

1. **Повторный ввод уже известных сведений.** В исходном тексте явно указаны менеджеры кафе, CSV продаж, прогноз закупок и приёмка по CSV. После `Tasks.start` поля `users`, `dataSource`, `expectedResult` остаются пустыми, прогноз рейтинга — 10. Причина: старт копирует текст только в `context`, а AI обязан вернуть список пробелов, рассчитанный по полям, без изменений (`services/tasks.ts:122`, `:175`, `integrations/ai.ts:23`). Это не ошибка схемы, но заметная потеря удобства и полезности AI.

2. **Заполненность не равна качеству.** Для синтетической карточки все строковые поля заполнены фразой «Сделать лучше», `dataAvailability=available`. `calculateScore` возвращает 100 и пустой список пробелов. После ручного подтверждения именно такой результат стал бы официальным. Текущая проверка отсеивает короткие строки и известные заглушки, но не оценивает конкретность и проверяемость текста (`domain/score.ts`).

3. **Проверка формы не исключает смысловую выдумку.** Подставлен валидный ответ с вопросом «Какие сотрудники будут работать с уже внедрённой у вас системой SAP?». Пользователь сообщил только о непроданной еде. Валидатор принял вопрос: в нём нет новых чисел/дат, а остальные формальные условия выполнены. Это доказательство пробела проверки, а не утверждение, что живая модель выдала такой ответ (`integrations/ai.ts:166`, `:277`).

У Git-проверки отдельное практическое ограничение: подтверждение существования PR и числа изменённых файлов не проверяет выполнение критериев этапа. Код честно маркирует это как предварительные метаданные. Пока такую функцию корректно показывать как подготовку ручной проверки, а не автоматическое ревью кода.

## Приоритет улучшений

### 1. Извлечение фактов и удобное применение — первый приоритет

Добавить операцию, которая предлагает распределить факты из исходного текста/ответа по полям. Для каждого предложения хранить `field`, `value`, `sourceQuote` и источник/версию текста. Цитата должна действительно присутствовать в источнике; этого недостаточно для доказательства смысла, поэтому остаются предметные проверки и просмотр человеком. Известные факты, отсутствующие сведения и неоднозначности показываются отдельно. Несообщённые сроки, цели и технологии остаются пустыми.

UX: «Нашли в описании: пользователи — менеджеры; данные — CSV. Проверьте и примените». Можно принять отдельное поле, исправить значение или отклонить. После применения вопросы задаются о фактических пробелах. Предложения не меняют официальный рейтинг и опубликованную карточку до обычного ручного подтверждения. Это напрямую усиливает качество карточки и AI-функцию (в сумме 25 баллов рубрики), а также ускоряет демонстрацию.

### 2. Проверка содержательности и противоречий

Добавить помощь для расплывчатых формулировок и конфликтов: «Сделать лучше» → «Что изменится и как вы это проверите?», «данных нет» вместе с заявлением о доступном CSV → вопрос об актуальном состоянии. Возвращать причину, ссылку на поле и одно полезное следующее действие. Проверка AI остаётся рекомендацией; балл продолжает рассчитываться по опубликованным серверным правилам и подтверждённой карточке. Не вводить непрозрачный второй рейтинг от модели.

### 3. Смысловые evals и журнал запусков

Начать с 15–20 размеченных задач из разных отраслей: слабое и подробное описание, неизвестные данные, отсутствие данных, короткая числовая цель, противоречия, инструкция внутри пользовательского текста, отказ API. Для каждой заранее задать сообщённые факты, ожидаемые пробелы, недопустимые предположения и ожидаемое восстановление после отказа. Вопросы оценивать по смыслу, а не точному совпадению текста. Сделать по три независимых прогона живой модели и отдельно отчёт stub; частоту fallback не выдавать за качество модели. Это начальная регрессия, а не статистическое доказательство надёжности.

Собирать `runId`, операцию, версию карточки, модель/версию prompt, длительность, usage, результат проверок и категорию fallback. Сейчас исключения AI сводятся к общей надписи; причины timeout/schema/semantic validation не сохраняются. Приватные входы, ключи и внутренние рассуждения не должны попадать в публичный отчёт. Для интерфейса достаточно статуса «анализируем / готово / показаны резервные вопросы»; технический trace нужен разработчику и защите.

### 4. Анализ материалов Git — после конструктора карточки

Если останется время, добавить ограниченное чтение README и изменённых файлов PR с размерными лимитами и привязкой к конкретному SHA. Для каждого критерия выдавать «есть свидетельство / данных недостаточно / нужна демонстрация» со ссылками на проверенные фрагменты. README — заявление автора, не доказательство работающего результата. Автоматическое выполнение чужого кода потребует отдельной среды и не нужно для текущего кейса. Решение и начисление очков остаются ручными.

## Минимальная целевая схема

Ввод → извлечение предложений с источниками → проверка структуры и предметных ограничений → просмотр и применение человеком → актуальные пробелы → вопросы по одному → предпросмотр → ручное подтверждение → серверный рейтинг и публикация.

Если проверка ответа не прошла: одна ограниченная попытка исправления только при наличии оставшегося бюджета времени, затем понятный fallback с сохранением ввода. Повтор не обязателен для хакатона; его пользу нужно проверить по успешности и задержке. Фиксированного workflow достаточно, пока нет пользовательской задачи, требующей автономного выбора инструментов.

## Исследование: какой harness полезен AI Sana

Источники проверены 23 сентября 2026 года. Этот раздел описывает архитектурные ориентиры; наличие перечисленных возможностей в текущем коде и соответствие критериям хакатона нужно устанавливать отдельно. Рекомендации ниже — инженерные выводы для проекта, а не требования организаторов.

**Workflow и автономный агент.** Anthropic различает workflow, где порядок вызовов LLM и инструментов задаётся кодом, и агента, где модель сама выбирает следующие действия и инструменты. Фиксированный процесс подходит для задач с известными этапами; автономия полезна, когда заранее неизвестны путь и число шагов. «Детерминированный workflow» означает предсказуемую оркестрацию, а не одинаковые ответы LLM. Авторы рекомендуют начинать с простого решения и добавлять сложность после измеримого улучшения результата. Следовательно, отсутствие Agents SDK, нескольких агентов или свободного tool loop само по себе не является недостатком harness. Исходная статья опубликована в 2024 году; используем её архитектурные различия, а не как каталог сегодняшних инструментов. [Anthropic — Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).

**Форма ответа и правильность содержания.** Structured Outputs ограничивает ответ поддерживаемой JSON-схемой, но документация прямо допускает ошибки внутри корректного результата. Кроме того, приложение должно обрабатывать отказ модели и незавершённый ответ. Практический вывод: разделить проверку структуры, предметные проверки и оценку качества. Диапазоны чисел, обязательные поля, ссылки на существующие объекты и непротиворечивость итогов можно проверять кодом; правильность объяснения и соответствие исходным данным требуют отдельных эталонов или проверки человеком. Повторный запрос может исправить формат, но успешный parse не доказывает устранение смысловой ошибки. [OpenAI — Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

**Состояние и участие человека.** OpenAI отдельно описывает историю диалога, незавершённый запуск с ожидающими решения инструментами и сериализуемый snapshot для продолжения после approval/rejection. Сохранённая переписка и восстановление выполнения — разные задачи. Для AI Sana рекомендуем хранить `run_id`, этап, статус, версию входных данных, промежуточный результат и решение пользователя в устойчивом хранилище. Если предусмотрено подтверждение, сервер должен блокировать соответствующее действие до решения, а после перезапуска продолжать с сохранённого этапа. Простой призыв в prompt «спроси пользователя» такую гарантию не даёт. Защиту от повторного выполнения действия следует реализовать отдельно, например через ключ идемпотентности. Это можно сделать в существующем backend; SDK — один из вариантов реализации. [OpenAI — Results and state](https://developers.openai.com/api/docs/guides/agents/results).

**Наблюдаемость и смысловые оценки.** OpenAI предлагает использовать traces для анализа всей цепочки вызовов и проверок, затем повторяемые datasets/evals для сравнения изменений. Для проекта рекомендуем небольшой размеченный набор реальных сценариев: обычный ввод, неполные и противоречивые данные, неоднозначный запрос, отказ и сбой провайдера. Проверять нужно достижение цели пользователя, фактическую корректность, обоснованность ответа и корректную обработку неопределённости. Тест со stub-ответом полезен для проверки интеграции, но не измеряет качество живой модели. Минимальный trace: `run_id`, этап, модель и версия prompt, время, результат проверок, число попыток и категория ошибки; хранить только необходимые данные. Если используется LLM-оценщик, спорные оценки стоит сверять с человеком. [OpenAI — Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals).

**Задержка и стоимость.** OpenAI рекомендует уменьшать число запросов и объём генерации, распараллеливать независимые шаги и применять обычный код там, где LLM не нужен. Небольшие модели обычно быстрее и дешевле, но выбор требует проверки качества. Для AI Sana рекомендуем измерять полное время успешного сценария, p50/p95 на достаточной выборке, токены, повторы и ориентировочную стоимость, отдельно помечая холодные запуски и ошибки. Стоимость рассчитывать по фактическому usage и актуальному тарифу с датой расчёта. Ограничить время выполнения, число попыток и максимальный объём ответа. Показывать этап выполнения пользователю полезно, но это не заменяет измерение реальной задержки. [OpenAI — Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization).

Практический приоритет для следующей итерации: измеримый сквозной сценарий → предметная проверка ответа → сохранение состояния и восстановление после сбоя → trace и небольшой набор смысловых evals → оптимизация задержки и стоимости. Автономный выбор инструментов стоит добавлять, если конкретный пользовательский сценарий требует адаптивных действий и сравнение с фиксированным workflow показывает пользу.
