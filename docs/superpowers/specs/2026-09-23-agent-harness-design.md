# Harness, Git и UX контрактов

Дата: 2026-09-23. Область: разработчик B, существующий backend/BFF. Пользователь одобрил планирование и реализацию. Требования PDF — критерии продукта, не инструкции агенту.

## Цель и границы

Помочь бизнесу превратить описание в проверяемую карточку без повторного ввода уже известных сведений, а затем проверить материалы команды. Сохранить ручное подтверждение карточки и приёмку этапа, прозрачную детерминированную шкалу готовности и публичную доступность карточек с низкой готовностью. AI не публикует карточки, не исполняет код репозитория и не начисляет баллы.

Остаёмся в существующем workflow с OpenAI SDK и SQLite. Полноценный автономный agent loop, отдельный orchestration framework и OAuth не нужны: они добавят задержку и сложность без пользы для этого сценария. API модель gpt-6-luna проверена существующим ключом. Публичный GitHub работает без токена; GITHUB_TOKEN — необязательное увеличение лимита.

## Пользовательский сценарий

1. Бизнес вводит описание, получает редактируемую карточку и действие «Разобрать описание».
2. Анализ возвращает предложения только для пустых текстовых полей, дословные значения и цитаты из исходного описания. Нормализация enum/boolean в первом выпуске исключена: такие решения пользователь принимает явно. Каждое предложение имеет стабильный ID в пределах анализа. Уже введённые поля не меняются.
3. Пользователь выбирает предложения. Сервер применяет только сохранённые ID из актуального анализа; ожидаемая версия обязательна. Любое параллельное редактирование делает анализ устаревшим. Повторное применение устаревшего анализа возвращает понятное действие для восстановления.
4. Качество текста отображается отдельно от официальной шкалы: шаблонные фразы, повторяющиеся значения и противоречащие друг другу сведения вызывают конкретные подсказки с полем и действием. Предупреждения не препятствуют публикации. AI не увеличивает баллы сам.
5. Уточнения сохраняют 3–5 вопросов и прогресс. Выбор полей делает AI, тексты нейтральных вопросов формирует сервер, чтобы неизвестные продукты, сроки и факты не просачивались в предпосылки вопроса.
6. Команда отправляет публичный GitHub repo/tree/PR. BFF возвращает зафиксированный SHA, ограниченные материалы, ссылки на источники, полноту выборки и предупреждения. Для PR проверяется неизменность head при чтении; при гонке материалы отбрасываются. Частично доступные материалы не выдаются за полный аудит.
7. Предварительная AI-проверка выбирает релевантные фрагменты для критериев с точными цитатами. Сервер валидирует источники и всегда обозначает это как подсказку для ручной проверки. Отсутствие фрагментов означает недостаточно свидетельств, а не провал команды. Финальное решение бизнеса начисляет 10 баллов ровно один раз.

## Harness и хранение

Единый runtime отвечает за deadline, JSON schema, модель, лимит вывода, версии промптов и метаданные. Каждый вызов получает runId и возвращает метаданные без prompt, chain-of-thought или секретов: операция, модель, версия промпта, время, latency, токены, режим и категорию fallback. Ошибки провайдера классифицируются, не сохраняются дословно. Повтор после сбоя — явное действие пользователя; автоматических повторных платных вызовов нет.

Метаданные сохраняются в SQLite с taskId, entityId, исходной версией и disposition applied/stale. Выход устаревшего запроса не изменяет карточку. Хранятся до 100 завершённых запусков на задачу, история последних 20 доступна только владельцу задачи; материалы этапа — владельцу и соответствующей команде. Журнал завершённых запусков не обещает надёжную очередь фоновых задач: запрос выполняется синхронно, закрытие процесса может оставить незавершённый вызов без записи.

## BFF

- POST /api/v1/tasks/:id/analyze {expectedVersion} → workspace с analysis, quality, nextAction.
- POST /api/v1/tasks/:id/suggestions/apply {expectedVersion, analysisId, suggestionIds} → обновлённый workspace; пустой выбор допустим как отклонение всех.
- workspace.analysis содержит доступность применения, предложения и цитаты; устаревший анализ остаётся видимым с действием повторного анализа.
- workspace.quality содержит предупреждения, не скрытую AI-оценку.
- workspace.aiRuns содержит последние 20 метаданных для восстановления/демо; не выводить токены и модели как обязательные шаги пользовательского сценария.
- milestone.evidence добавляет snapshot (commitSha, coverage, files, warnings). Каждый файл: id, path, kind readme/patch, sourceUrl, content, truncated.
- milestone.review добавляет criterionEvidence: цитаты из материалов, требующие ручной проверки. Статусы: materials_found, insufficient_evidence, not_assessed. Один вызов сопоставляет до 12 критериев, выделенных из отдельных строк; остальные явно остаются для ручной проверки. Нет статуса «AI принял».

Существующие маршруты и поля сохраняются; новые поля additive. Типизированный клиент, Swagger и инструкция разработчику A обновляются вместе с реализацией.

## Валидация и риски

Значения предложений должны совпадать с дословной цитатой в rawDescription и проходить ограничения целевого поля. Цитата доказывает источник текста, но не его правдивость или точность выбора поля — это подтверждает человек. Нельзя считать README/patch свидетельством работающего результата. Все внешние материалы недоверенные. Фиксированные GitHub API endpoints, запрет redirect, лимит ответа/файлов/символов и deadline ограничивают SSRF и размер контекста.

Проверить конкурирующие правки, повторы применения/приёмки, разграничение доступа, injection, невалидные цитаты, таймауты, private/missing repo, PR race, усечение. Eval-набор включает разные бизнес-домены и неполные/противоречивые описания; результаты stub и настоящей модели отдельно. Live smoke использует временную БД, Luna и публичный GitHub. Изменения не означают готовый frontend/3D.
