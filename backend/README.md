# AI Sana — backend разработчика B

Сервер P0/P1 для конструктора бизнес-задач, общего каталога 2D/3D, откликов и подтверждённых этапов команд. Это BFF для экранов веб-приложения: команда возвращает обновлённый экран, подсказку следующего действия и разрешённые кнопки. Фронтенд и 3D разрабатываются отдельно.

## Запуск

Нужен Node.js 22.12+ и npm. Все команды выполняются в `backend/`:

```sh
npm ci
cp .env.example .env
npm run dev
```

PowerShell: `Copy-Item .env.example .env`. Не перезаписывайте существующий `.env` с ключом. Для живого AI нужен `OPENAI_API_KEY` в `backend/.env`; без него приложение работает с явно обозначенным fallback. По умолчанию `OPENAI_MODEL=gpt-6-luna`, reasoning `low`, `AI_MODE=auto`, `AI_TIMEOUT_MS=30000`, `AI_MAX_OUTPUT_TOKENS=4096`, `GIT_MODE=real`, `GIT_TIMEOUT_MS=15000`. Модель и лимиты можно переопределить через `.env`. `GITHUB_TOKEN` необязателен: публичные GitHub repo/PR доступны и без него; токен повышает лимит запросов. Ключи никогда не отправляются в браузер и не коммитятся.

- API: `http://localhost:3001/api/v1/health`
- Swagger UI: `http://localhost:3001/api/docs`
- OpenAPI: `http://localhost:3001/api/openapi.json`
- При первом старте SQLite и тестовые данные создаются автоматически. Коды входа находятся только в **локальном** `demo-accounts.local.json`. В Git этот файл не попадает.
- 2 бизнеса и 5 команд; 5 черновиков, 5 опубликованных задач всех четырёх уровней, 5 откликов. Повторный seed не перезаписывает изменения. Отдельная команда: `npm run seed`.

Для сборки: `npm run build`, затем `npm start`. Данные хранятся в `data/ai-sana.db` и переживают перезапуск.

Фронтенд Vite можно запустить на `localhost:5173`. Для единого сервера задайте `FRONTEND_DIST=../frontend/dist` после сборки фронтенда. `ALLOWED_ORIGINS` — точный список разрешённых origin через запятую. Для доступа по LAN задайте `HOST=0.0.0.0` и добавьте фактический origin интерфейса в список. Это локальный демо-сервер, не готовая инфраструктура для публичного развёртывания.

## Интеграция фронтенда

Полная памятка: [docs/backend-integration.md](../docs/backend-integration.md). Типизированный браузерный клиент: [client/index.ts](client/index.ts). Основной префикс `/api/v1`, а не набор CRUD-маршрутов из предварительного ТЗ.

Финальное ревью потребителей: [бизнес и группа](../docs/consumer-ux-review.md). Карточка группы теперь даёт `participation.nextAction` с адресатом перехода, отклики — русские статусы, кабинет бизнеса — только доступные проверки. Замечания бизнеса сохраняются в приватной истории после повторной сдачи. Новых маршрутов эти улучшения не требуют.

Вход `POST /api/v1/session/start` с `{ "code": "локальный код" }` возвращает `token`, `actor`, `expiresAt`. Передавайте `Authorization: Bearer ...`. Для двух ролей в двух вкладках храните токен в `sessionStorage`. Создание команды `POST /teams/start` возвращает её код один раз; остальные участники входят по тому же коду.

`GET /bootstrap`, `/catalog`, `/dashboard`, `/tasks/:id`, `/tasks/:id/workspace`, `/tasks/:id/review`, `/milestones/:id`, `/scoreboard` возвращают готовые модели экранов. `/snapshot` объединяет основные данные для начальной загрузки/переподключения. Каталог содержит и отсортированные карточки, и страницы 3D-павильонов по пять с устойчивым порядком публикации. В каталоге фильтры `industry`, `level`, `search`; `page`, `pageSize`, `worldPage` независимы.

Команды с редактированием требуют `expectedVersion` из соответствующего объекта (`task`, `proposal` или `milestone`). При 409 `STALE_VERSION` сохраните пользовательский ввод, загрузите свежий экран и предложите применить правки повторно. Не повторяйте устаревшую команду автоматически. Создание задачи/отклика/этапа поддерживает `Idempotency-Key`; используйте один ключ на одну логическую отправку и её сетевые повторы.

Версию задачи для редактирования берите из `workspace.task.version`: активность команд её не меняет. Публичная `card.version` и версия realtime-события отражают всю активность; это отдельный счётчик. Существующие сохранённые задачи совместимы без сброса базы.

`analyzeTask` предлагает заполнить пустые текстовые поля точными цитатами из `rawDescription`. Пользователь выбирает сохранённые ID предложений; `applySuggestions` принимает `expectedVersion`, `analysisId`, `suggestionIds`. Пустой массив отклоняет все предложения. Применение меняет только черновик, завершает текущий анализ и не обновляет официальный балл до подтверждения. `workspace.analysis` содержит `status` (`ready`, `empty`, `stale`, `resolved`), `canApply` и цитаты; любая последующая правка редактора делает неприменённый анализ устаревшим. `workspace.quality` — объяснимые подсказки о шаблонных фразах, повторениях и явных противоречиях, без изменения баллов или запрета публикации.

Уточнения сохраняются вместе с ответами. AI выбирает поля для 3–5 вопросов, сервер возвращает нейтральный текст из своего каталога. BFF отдаёт `clarification.nextQuestion`, тип поля и варианты, прогресс и весь список для возврата назад. `confirm` завершает текущие уточнения (`reviewed=true`), даже если часть ответов пока неизвестна; явный повторный `clarify` открывает новый сеанс. Неприменимые вопросы пропускаются, включая альтернативу «метрика с целью или условие приёмки».

`pendingMilestones` на станции и `teamProgress.statusLabel` в карточке показывают «На проверке». Приватный этап получает `statusLabel/statusHint` для текущей роли. Отправка, возврат и подтверждение обновляют маркеры через realtime; создание команды обновляет открытый рейтинг событием `team.created` без секретов входа.

Socket.IO: подключение с `auth: { token }` или без токена для гостя. События `invalidate` и `sync.required` требуют перечитать затронутый экран. Данные событий содержат ID/версию, без текста черновиков и предложений. При каждом `connect` заново загружайте снимок: сокеты не заменяют SQLite и HTTP. При выходе сокет с этой сессией отключается.

## Бизнес-правила

Два независимых показателя: готовность карточки 0–100 и очки выбранной команды. Начисление готовности происходит по подтверждённому снимку. Сохранение черновика показывает прогноз, но не меняет публичную карточку. Повторное подтверждение уже опубликованной карточки сразу обновляет её публичный снимок, включая название и отрасль. Удаление данных может снизить оценку.

| Категория | Баллы |
|---|---:|
| Текущая ситуация + потребность | 10 + 10 |
| Известная доступность данных + реальный доступный источник | 10 + 10 |
| Конкретный ожидаемый результат | 15 |
| Показатель и цель **или** условие приёмки | 15 |
| Ограничения **или** явно подтверждённое отсутствие | 10 |
| Пользователи | 10 |
| Контакт + формат консультаций | 5 + 5 |

Пустые/шаблонные строки не дают очков. `dataAvailability=none` даёт 10, но не изображает наличие датасета. Сервер проверяет структурные условия и типовые заглушки; содержательность текста подтверждает бизнес. Это объяснимая эвристика полноты, не автоматическая экспертиза качества описания.

Уровни: 0–39 `draft`, 40–69 `working`, 70–89 `ready`, 90–100 `priority`. Уровень `draft` не равен статусу публикации. Любая опубликованная задача доступна для отклика. Сортировка: оценка по убыванию, более новая публикация выше, затем ID. Мир: время публикации по возрастанию, затем ID, страницы по 5. Количество откликов не ограничено; несколько предложений одной команды допустимы.

Бизнес независимо выбирает/отклоняет отклики. Выбранная команда создаёт один этап на задачу с критерием приёмки и фиксированными 10 очками. Отправка Git-ссылки переводит этап в `in_review`, очков не даёт. Бизнес подтверждает или возвращает с объяснением. Подтверждение и уникальная запись начисления выполняются в одной SQLite-транзакции; повторы не удваивают очки. У каждой выбранной команды свой этап. Утверждённый этап неизменяемый; отменить последний выбор команды после утверждения нельзя.

## OpenAI и Git

`src/integrations/ai.ts` содержит выбор полей для вопросов, проверку этапа, `createAiProvider` и fallback; `analysis.ts` — извлечение цитат и проверку источников; `ai-runtime.ts` — общий вызов и метаданные. Официальный SDK использует Responses API, `zodTextFormat`, `store:false`, deadline и `maxRetries:0`. По умолчанию это один вызов `gpt-6-luna` с reasoning `low`, лимитом 30 секунд и 4096 выходных токенов на операцию. Платных автоматических повторов нет; повторный запуск — явное действие пользователя. Это фиксированный workflow, модель не выбирает инструменты и не ведёт автономный цикл.

Разбор получает `{ rawDescription, fields }`, модель возвращает `{ suggestions: [{ field, quote }] }`. Сервер допускает только точный непрерывный фрагмент исходного `rawDescription`, проверяет ограничение целевого поля, уникальность поля и отсутствие уже сохранённого значения. `value` равен `source.quote`. Поля `dataAvailability` и `noConstraints` пользователь задаёт сам. Дословная цитата подтверждает источник текста, но не его правдивость или правильность выбора поля: каждое предложение проверяет человек. Fallback разбора возвращает пустые предложения и возможность заполнить карточку вручную.

Вход уточнения: `{ rawDescription, fields, missingFields }`. Выход BFF: `{ missingFields, questions: [{ field, text }], mode, warning, run }`. Вопросов 3–5; при малом числе пробелов оставшиеся проверяют заполненные поля. Модель выбирает поля, а **пользовательский текст вопросов формирует сервер** из нейтрального каталога после валидации. Ответы за бизнес не генерируются. Некорректная структура, отказ или недоступность API дают `mode=stub` и вопросы по шаблону. `AI_MODE=stub` принудительно включает этот режим. Fallback не блокирует ручное заполнение, подтверждение и публикацию.

`GitProvider.inspect(url)` заменяем: `GIT_MODE=real` проверяет только публичные GitHub repo/PR/`tree/ref` через фиксированный REST-хост. `GIT_MODE=mock` возвращает `provider=mock`; другие допустимые HTTPS-хосты остаются для ручной проверки. Приватные репозитории исключены даже с токеном. Сервер фиксирует SHA, читает README и первую страницу patch PR. Лимиты: **8 материалов, 6000 символов на материал, 24000 символов всего, 256 KiB на JSON-ответ GitHub**, по умолчанию 15 секунд на инспекцию. Redirect запрещён; сервер не клонирует репозиторий, не исполняет код и не запускает его тесты. Для PR повторно проверяются head, base и число файлов; при изменении или невозможности проверки материалы отбрасываются.

Для текущей версии выбрана автоматическая проверка публичных материалов. Ссылку на приватный GitHub можно отправить как свидетельство, но провайдер вернёт `unavailable`: бизнес проверяет её вручную со своим доступом, AI не делает выводов о закрытом содержимом. Приватность репозитория самого проекта не меняется; для демонстрации этой интеграции используются публичные ссылки.

`evidence.snapshot` содержит `commitSha`, `inspectedAt`, `coverage`, `files`, `warnings`; каждый материал — `id`, `path`, `kind`, `sourceUrl`, `content`, `truncated`. `complete` означает полноту **ограниченной выборки**, `partial` — частичные/усечённые материалы, `metadata_only` — отсутствие прочитанных материалов. Даже `verified` и `complete` не подтверждают работающий результат. При отказе GitHub ссылка и описание команды сохраняются для ручной проверки, но недоступные материалы не считаются прочитанными.

Для этапа модель выбирает `factIndexes` из проверенных метаданных, `checkIds` из серверного каталога и при наличии материалов — `criterionMatches` с точными цитатами. BFF возвращает `review.criterionEvidence`: критерий, статус `materials_found`, `insufficient_evidence` или `not_assessed`, цитаты со ссылками и следующий шаг ручной проверки. `not_assessed` явно обозначает пропущенную оценку при доступных материалах, в том числе fallback и критерии за пределами первых 12 строк, доступных модели за вызов. README — заявление автора со ссылкой на blob SHA, patch — текст изменений со ссылкой на сравнение base SHA и head SHA. Цитата не доказывает выполнение критерия; отсутствие цитаты не означает провал команды. Решение остаётся за бизнесом, который подтверждает этап и начисляет 10 очков ровно один раз.

SQLite хранит последние **100 завершённых AI-запусков на задачу**, приватный workspace владельца показывает последние **20** в `aiRuns`. Метаданные включают операцию, модель/версию prompt, время, длительность, usage, валидацию, причину fallback, исходную версию и `disposition=applied|stale`. `applied` означает сохранение результата вызова, а не согласие человека с предложениями. В журнале нет prompt, сырых ответов, ключей и внутренних рассуждений. Это история завершённых синхронных запросов: статуса выполнения, фоновой очереди и возобновления после остановки процесса нет. UI показывает собственное состояние ожидания, сохраняет ввод и допускает ручное продолжение; после потери ответа сначала перечитывает экран.

## Проверки и сдача

```sh
npm run check
npm test
npm run build
npm run demo
npm run preflight
npm run eval
npm run eval -- --live --repeat=3
```

`demo` запускает изолированный временный сервер и через HTTP проходит новый пример кафе, разбор с применением цитат, уточнение, два отклика, выбор двух команд, этап, свидетельство, подтверждение и повтор без двойного начисления. По умолчанию внешние провайдеры в stub/mock; для живой проверки с ключом: `npm run demo -- --live`. Живой HTTP demo 23 сентября 2026 прошёл с Luna, цитатами Git-материалов, тремя записями истории и командой подтверждения от бизнеса: 10 очков без повторного начисления. Решение пользователя имитирует smoke-скрипт; публичная ссылка служит для проверки интеграции, а не доказательства бизнес-результата из примера.

`preflight` требует `OPENAI_API_KEY`: проверяет доступность настроенной модели, публичный репозиторий и найденный публичный PR с материалами. Живая проверка 23 сентября 2026 успешно прошла для модели, repo и PR; публичный GitHub работал без токена. Это проверка подключения, а не качества модели или выполнения бизнес-критериев. Команды находятся в [scripts/preflight.ts](scripts/preflight.ts), [scripts/eval.ts](scripts/eval.ts), сценарии — в [scripts/eval-cases.ts](scripts/eval-cases.ts).

`eval` без `--live` проверяет контракт stub; живой вариант расходует API-токены. Набор содержит 15 синтетических сценариев извлечения: точность цитат, ожидаемые поля, запрет неподтверждённых предположений и сохранение правок. `--repeat=1..3`, `--output=путь` управляют повторениями и файлом. По умолчанию отчёты пишутся в `docs/evals/stub-harness-report.json` и `docs/evals/live-harness-report.json`; включают режим, модель, успешность, fallback, p50/p95 и usage. [Живая серия от 23 сентября 2026](../docs/evals/live-harness-report.json): **45/45**, без fallback, p95 **4853 мс**. Это начальная регрессия извлечения, без полной смысловой или UX-оценки; успешный preflight сам по себе не измеряет качество модели.

Тесты покрывают формулу и границы, права, изоляцию черновиков, конфликты версий, идемпотентность, сохранение после открытия БД, сквозные роли, реальный SDK с тестовыми HTTP-ответами, Git-провайдер, два сокета, переподключение и выход. Ограничения: один процесс/SQLite, один этап на команду и задачу, вход по демо-кодам, без приватного Git/OAuth и фоновых webhooks. Производительность и работа 3D проверяются в реализации фронтенда.

## Устройство

`contracts.ts` — схемы входа и доменные типы; `domain/score.ts` — формула; `services/` — сценарии и инварианты; `db.ts` — таблицы и транзакции; `auth.ts` — хешированные коды/сессии; `views.ts` — экранные ответы; `app.ts` — HTTP; `realtime.ts` — события после сохранения; `integrations/` — заменяемые внешние зависимости.
