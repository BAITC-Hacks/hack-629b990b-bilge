# AI Sana — backend разработчика B

Сервер P0/P1 для конструктора бизнес-задач, общего каталога 2D/3D, откликов и подтверждённых этапов команд. Это BFF для экранов веб-приложения: команда возвращает обновлённый экран, подсказку следующего действия и разрешённые кнопки. Фронтенд и 3D разрабатываются отдельно.

## Запуск

Нужен Node.js 22.12+ и npm. Все команды выполняются в `backend/`:

```sh
npm ci
cp .env.example .env
npm run dev
```

PowerShell: `Copy-Item .env.example .env`. Не перезаписывайте существующий `.env` с ключом. Укажите свой `OPENAI_API_KEY`, при необходимости `OPENAI_MODEL`. По умолчанию `gpt-4o-mini`, `AI_MODE=auto`, `GIT_MODE=real`. Ключи никогда не отправляются в браузер и не коммитятся.

- API: `http://localhost:3001/api/v1/health`
- Swagger UI: `http://localhost:3001/api/docs`
- OpenAPI: `http://localhost:3001/api/openapi.json`
- При первом старте SQLite и тестовые данные создаются автоматически. Коды входа находятся только в **локальном** `demo-accounts.local.json`. В Git этот файл не попадает.
- 2 бизнеса и 5 команд; 5 черновиков, 5 опубликованных задач всех четырёх уровней, 5 откликов. Повторный seed не перезаписывает изменения. Отдельная команда: `npm run seed`.

Для сборки: `npm run build`, затем `npm start`. Данные хранятся в `data/ai-sana.db` и переживают перезапуск.

Фронтенд Vite можно запустить на `localhost:5173`. Для единого сервера задайте `FRONTEND_DIST=../frontend/dist` после сборки фронтенда. `ALLOWED_ORIGINS` — точный список разрешённых origin через запятую. Для доступа по LAN задайте `HOST=0.0.0.0` и добавьте фактический origin интерфейса в список. Это локальный демо-сервер, не готовая инфраструктура для публичного развёртывания.

## Интеграция фронтенда

Полная памятка: [docs/backend-integration.md](../docs/backend-integration.md). Типизированный браузерный клиент: [client/index.ts](client/index.ts). Основной префикс `/api/v1`, а не набор CRUD-маршрутов из предварительного ТЗ.

Вход `POST /api/v1/session/start` с `{ "code": "локальный код" }` возвращает `token`, `actor`, `expiresAt`. Передавайте `Authorization: Bearer ...`. Для двух ролей в двух вкладках храните токен в `sessionStorage`. Создание команды `POST /teams/start` возвращает её код один раз; остальные участники входят по тому же коду.

`GET /bootstrap`, `/catalog`, `/dashboard`, `/tasks/:id`, `/tasks/:id/workspace`, `/tasks/:id/review`, `/milestones/:id`, `/scoreboard` возвращают готовые модели экранов. `/snapshot` объединяет основные данные для начальной загрузки/переподключения. Каталог содержит и отсортированные карточки, и страницы 3D-павильонов по пять с устойчивым порядком публикации. В каталоге фильтры `industry`, `level`, `search`; `page`, `pageSize`, `worldPage` независимы.

Команды с редактированием требуют `expectedVersion` из соответствующего объекта (`task`, `proposal` или `milestone`). При 409 `STALE_VERSION` сохраните пользовательский ввод, загрузите свежий экран и предложите применить правки повторно. Не повторяйте устаревшую команду автоматически. Создание задачи/отклика/этапа поддерживает `Idempotency-Key`; используйте один ключ на одну логическую отправку и её сетевые повторы.

Версию задачи для редактирования берите из `workspace.task.version`: активность команд её не меняет. Публичная `card.version` и версия realtime-события отражают всю активность; это отдельный счётчик. Существующие сохранённые задачи совместимы без сброса базы.

Уточнения сохраняются вместе с ответами. BFF отдаёт `clarification.nextQuestion`, тип поля и варианты, прогресс и весь список для возврата назад. `confirm` завершает текущие уточнения (`reviewed=true`), даже если часть ответов пока неизвестна; явный повторный `clarify` открывает новый сеанс. Неприменимые вопросы пропускаются, включая альтернативу «метрика с целью или условие приёмки».

`pendingMilestones` на станции и `teamProgress.statusLabel` в карточке показывают «На проверке». Приватный этап получает `statusLabel/statusHint` для текущей роли. Отправка, возврат и подтверждение обновляют маркеры через realtime; создание команды обновляет открытый рейтинг событием `team.created` без секретов входа.

Socket.IO: подключение с `auth: { token }` или без токена для гостя. События `invalidate` и `sync.required` требуют перечитать затронутый экран. Данные событий содержат ID/версию, без текста черновиков и предложений. При каждом `connect` заново загружайте снимок: сокеты не заменяют SQLite и HTTP. При выходе сокет с этой сессией отключается.

## Бизнес-правила

Два независимых показателя: готовность карточки 0–100 и очки выбранной команды. Начисление готовности происходит по подтверждённому снимку. Сохранение черновика показывает прогноз, но не меняет публичную карточку. Повторное подтверждение уже опубликованной карточки сразу обновляет её публичный снимок, включая название и отрасль. Удаление данных может снизить оценку.

| Категория | Баллы |
|---|---:|
| Текущая ситуация + потребность | 10 + 10 |
| Известная доступность данных + реальный доступный источник | 10 + 10 |
| Конкретный ожидаемый результат | 15 |
| Показатель и цель **или** условие приёмки | 15 |
| Ограничения **или** явно подтверждённое отсутствие | 10 |
| Пользователи | 10 |
| Контакт + формат консультаций | 5 + 5 |

Пустые/шаблонные строки не дают очков. `dataAvailability=none` даёт 10, но не изображает наличие датасета. Сервер проверяет структурные условия и типовые заглушки; содержательность текста подтверждает бизнес. Это объяснимая эвристика полноты, не автоматическая экспертиза качества описания.

Уровни: 0–39 `draft`, 40–69 `working`, 70–89 `ready`, 90–100 `priority`. Уровень `draft` не равен статусу публикации. Любая опубликованная задача доступна для отклика. Сортировка: оценка по убыванию, более новая публикация выше, затем ID. Мир: время публикации по возрастанию, затем ID, страницы по 5. Количество откликов не ограничено; несколько предложений одной команды допустимы.

Бизнес независимо выбирает/отклоняет отклики. Выбранная команда создаёт один этап на задачу с критерием приёмки и фиксированными 10 очками. Отправка Git-ссылки переводит этап в `in_review`, очков не даёт. Бизнес подтверждает или возвращает с объяснением. Подтверждение и уникальная запись начисления выполняются в одной SQLite-транзакции; повторы не удваивают очки. У каждой выбранной команды свой этап. Утверждённый этап неизменяемый; отменить последний выбор команды после утверждения нельзя.

## OpenAI и Git

`src/integrations/ai.ts` содержит точные промпты, `createAiProvider` и локальный fallback. Официальный SDK использует Responses API, `zodTextFormat`, `store:false`, явный тайм-аут без бесконечных повторов. Вход уточнения: `{ rawDescription, fields, missingFields }`. Выход: `{ missingFields, questions: [{ field, text }], mode, warning }`. Вопросов 3–5; при малом числе пробелов оставшиеся проверяют заполненные поля. Ответы не генерируются за бизнес: пользователь редактирует и подтверждает сведения. Некорректная структура, повторяющиеся вопросы, отказ или недоступность API дают явно обозначенный `mode=stub` и подходящие вопросы по шаблону. `AI_MODE=stub` принудительно включает этот режим.

ИИ-проверка этапа — предварительный список проверок. Факты о Git берутся только из проверенных метаданных. Модель не подтверждает достижение бизнес-результата. Любой AI-текст следует показывать как помощь, оставляя ручную проверку человеку.

Внутренний ответ модели для анализа этапа: `{ factIndexes, checkIds }`. Факты выбираются по индексам из проверенных метаданных, а текст проверок — из серверного каталога. Произвольные утверждения модели о выполнении этапа не публикуются. Уточняющие вопросы дополнительно проверяются на новые числа и сроки, отсутствующие во входе; это консервативная проверка, а не полная семантическая экспертиза.

`GitProvider.inspect(url)` заменяем: `GIT_MODE=real` проверяет публичные репозитории GitHub, PR и `tree/ref` через REST; `GIT_MODE=mock` явно возвращает `provider=mock`. Другие HTTPS-хосты сохраняются для ручной проверки. Отказ GitHub/лимит/тайм-аут не теряет материалы и не блокирует ручную проверку. Необязательный `GITHUB_TOKEN` повышает доступный лимит, но приватные репозитории всё равно исключены. Содержимое репозитория не исполняется, ссылка не клонируется. GitHub OAuth не требуется.

## Проверки и сдача

```sh
npm run check
npm test
npm run build
npm run demo
```

`demo` запускает изолированный временный сервер и через HTTP проходит новый пример кафе, два отклика, выбор двух команд, этап, свидетельство, подтверждение и повтор без двойного начисления. По умолчанию внешние провайдеры в stub/mock; для живой проверки с ключом: `npm run demo -- --live`. Синтетическая ссылка демонстрирует метаданные Git, а не реальный бизнес-результат.

Тесты покрывают формулу и границы, права, изоляцию черновиков, конфликты версий, идемпотентность, сохранение после открытия БД, сквозные роли, реальный SDK с тестовыми HTTP-ответами, Git-провайдер, два сокета, переподключение и выход. Ограничения: один процесс/SQLite, один этап на команду и задачу, вход по демо-кодам, без приватного Git/OAuth и фоновых webhooks. Производительность и работа 3D проверяются в реализации фронтенда.

## Устройство

`contracts.ts` — схемы входа и доменные типы; `domain/score.ts` — формула; `services/` — сценарии и инварианты; `db.ts` — таблицы и транзакции; `auth.ts` — хешированные коды/сессии; `views.ts` — экранные ответы; `app.ts` — HTTP; `realtime.ts` — события после сохранения; `integrations/` — заменяемые внешние зависимости.
